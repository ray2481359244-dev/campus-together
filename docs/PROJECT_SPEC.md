# 校园兴趣社区与智能组队平台项目书

版本：v1.0  
编制日期：2026年10月15日  
项目代号：CampusTogether  
产品中文名：待定，本文统一使用“校园兴趣社区与智能组队平台”  
适用阶段：参赛版本开发与单校试用  
项目属性：学生原创应用项目，采用 AI 辅助编程完成开发

本项目面向在校大学生，提供游戏、学习、竞赛、户外四个区域，每个区域包含讨论社区与招募大厅。用户可以围绕具体主题交流，发布带有时间、目标、人数和条件的招募，加入临时小队并在多人群聊中协作。参赛版本重点展示竞赛组队中的技能互补，同时完整保留四区统一体验。

本文既是项目立项与参赛说明，也是交给 Codex 的开发基线。开发目标是可安装、可运行、可由多个账号共同使用的全栈应用；界面原型、浏览器本地假数据和预设聊天演出均不能替代验收。项目正式名称、负责人、队员、指导教师、报名组别及正式截止日期由项目负责人补充，不预填未经确认的身份与赛事信息。

## 1 项目摘要

### 1.1 核心问题

大学生寻找同伴的过程常被拆散在讨论帖、班群、兴趣群和私聊中。知道谁感兴趣，并不等于知道谁有空、目标是否一致、能力是否适合。发布招募后，还要重复询问时间、剩余名额和联系方式；群满、活动结束或计划取消之后，原信息也可能继续传播。

这些是本项目需要验证的需求假设，不能直接写成已经完成的市场调研结论。首轮应访谈本校学生，确认问题出现的频率、现有解决方式与使用新平台的意愿。

### 1.2 产品解决方案

平台将内容交流与具体组队连接起来。讨论帖可关联招募，招募信息以结构化条件展示，符合条件的学生主动申请或加入，确认入队后进入该招募对应的临时群聊。队伍具有清晰状态和生命周期，用户能知道是否仍在招人、是否开始、是否结束。

AI 用于降低招募填写成本和解释组队建议。系统先依据明确条件进行筛选与评分，再在有真实模型服务时理解自然语言偏好、生成有依据的解释。时间、人数、学校范围等确定性约束由服务端规则处理。

### 1.3 首版交付目标

- 一个响应式 Web 应用，手机浏览器优先，兼容桌面演示。
- 四个区域及各自的讨论、招募入口，数据互相关联但权限明确。
- 真实注册登录、数据库持久化、招募加入与退出、多人文字群聊。
- AI 招募草稿生成与匹配解释；模型未配置时可完整使用普通表单和规则推荐。
- 基础内容管理、举报与封禁，以及可复现的测试和演示数据。
- 源码、启动说明、环境变量模板、数据迁移、测试记录及 AI 开发过程材料。

### 1.4 成功的判断方式

参赛版本首先证明一条完整流程：用户发现讨论，发布招募，系统解释条件，其他用户申请入队，队长确认，小队聊天并结束活动。其次通过同学试用验证是否减少反复沟通。没有真实试用结果之前，不宣称用户增长、获奖概率、匹配准确率或商业回报。

## 2 需求来源与决策边界

### 2.1 已明确的产品构想

以下内容来自本次讨论，应持续保留：面向在校大学生；四区结构为游戏、学习、竞赛和户外；每区均有讨论和招募；主题可由用户提出创建；不同游戏等主题有各自讨论空间；招募人能够设置要求；入队后提供临时多人群聊；同一机制可服务游戏搭子、学习搭子、参赛搭子和出游搭子。

### 2.2 本文采用的建议默认

为确保能直接开发，采用单校起步、Web 优先、四区共用基础模块、竞赛为重点演示场景的方案。点击详情不等于加入，明确点击申请或加入才触发入队；新增主题先申请并去重；聊天先支持文字；账号资料先自填并显示未核验；队伍总人数包含队长。

AI 招募生成、可解释匹配、招募状态管理、规则兜底和基础管理后台属于本项目书的实施建议，尚不能表述为用户逐项确认过的独立决定。Codex 默认按本文实施；负责人后续修改时应记录变更并同步接口、测试和文档。

### 2.3 赛事定位

项目计划用于此前讨论的全国高校 Vibe Coding 开发挑战赛方向。根据已提供的赛道介绍，项目应突出意图表达、AI 协同编码、架构理解、迭代与问题解决过程。应用内 AI 能力与 AI 辅助开发过程应分别展示，不能以一次模型调用替代开发过程证据。

正式申报前应核对当前报名赛道的原始文件，补齐作品形式、允许工具、源码与视频要求、截止日期、团队人数、第三方素材说明和评分项映射。本文不设定未经核实的官方评分权重或必选技术，也不承诺本方案天然满足全部赛事规则。

## 3 用户与使用场景

### 3.1 目标用户

首批用户为同一所高校内有兴趣交流、短期组队或持续协作需求的学生。产品通过学校范围、共同主题和可见活动条件减少沟通成本。首版不承担校方认证平台或校内官方活动系统的角色。

| 用户类型 | 主要需求 | 当前需验证的困难 | 产品提供的帮助 |
| --- | --- | --- | --- |
| 兴趣参与者 | 看讨论并找到同好 | 群多且内容杂，难定位具体主题 | 四区与主题筛选、相关招募 |
| 招募发起人 | 找到合适人数与角色 | 条件写不全，反复答复是否有位 | 结构化招募、申请审核、状态同步 |
| 招募参与者 | 判断自己能否参与 | 时间、目标和要求不清楚 | 条件对照、缺失信息提示、主动申请 |
| 竞赛队长 | 补齐团队技能 | 只看兴趣难判断能力互补 | 岗位需求、技能证据、时间匹配 |
| 平台管理员 | 维持基本秩序 | 重复主题、广告与违规内容 | 审核、隐藏、举报处理与审计 |

### 3.2 四个代表场景

游戏场景：用户在某游戏主题中浏览讨论，发布“今晚20点到22点休闲组队”，填写服务器、玩法和人数。其他用户确认时间及服务器后加入，满员后停止新成员进入，开始后群聊继续。

学习场景：用户发布周六图书馆高数复习招募，说明章节、时间、学习方式、预计人数及安静自习或讨论讲题的偏好。参与者先看学习节奏是否一致，再选择加入。

竞赛场景：用户发布应用开发比赛招募，说明已有后端能力，缺少前端与设计角色，每周可投入时间、目标及截止日期。系统解释申请者的技能与当前空缺是否对应，队长作最终决定。

户外场景：用户发布城市摄影步行活动，说明日期、集合区域、预算、强度与摄影主题。公开招募只展示粗粒度地点，确认入队后可在群公告中约定具体集合点。首版不提供实时定位和持续位置追踪。

### 3.3 用户需求验证

开发第一阶段访谈8至12名同学，四个场景尽量均有覆盖。记录最近一次找搭子的具体过程、耗时、失败原因、是否愿意使用新应用，以及最少需要公开哪些资料。访谈人数是计划值，不是完成值。

若需求验证发现用户更关心组队效率，应优先完善招募流程；若用户主要希望看内容，应记录为后续方向，不能在首版无边界扩展资讯运营、视频和推荐算法。

## 4 价值主张与差异化

### 4.1 产品价值

用户可以从具体讨论出发，形成带时间、名额与目标的小队。平台持续维护队伍状态，使招募信息反映当前可加入情况。队内协作入口随队伍建立，结束后保留有限的归档体验。

项目的差异化重点为场景条件、技能互补、时间可执行性和解释清楚的推荐。四个区域是信息组织方式，小红书式卡片是浏览表现形式，均不单独作为技术创新成果。

### 4.2 重点展示的三项设计

第一，讨论与行动关联。同一主题中的帖子可直接发起相关招募，招募也可返回来源讨论。用户能从“想了解”自然转到“想参与”。

第二，不同场景采用不同字段。游戏关注服务器与玩法，学习关注目标与方式，竞赛关注角色互补，户外关注日期预算和强度，避免用同一套兴趣标签替代所有条件。

第三，AI 降低填写门槛，规则保证条件可靠。推荐结果同时展示匹配依据、未确认事项与不满足条件，让用户理解建议，最终加入和批准均由人操作。

### 4.3 同类参考与竞争边界

公开参考包括 TRAE 社区的《校园搭子》以及《方遇》，前者介绍大学生搭子匹配与聊天，后者介绍内容社区、活动招募与自动建群。它们可用于观察功能重合与展示方式；作者介绍不等于独立验证的运行能力，也不构成其获奖或商业成功的证据。

本项目不宣称“首创校园搭子平台”。参赛陈述应具体说明自身完成了什么规则、解决了什么可观察的问题，以及试用中获得了什么证据。参考链接列于第25章。

## 5 版本范围与优先级

P0 表示应用核心闭环，必须先完成。P1 表示参赛增强，完整参赛版本应包含，但应在 P0 稳定后开发。P2 表示后续扩展，不得挤占当前关键路径。

| 优先级 | 范围 | 完成标准 |
| --- | --- | --- |
| P0 | 登录、资料、四区、主题、讨论、图文与评论 | 数据真实保存，权限正确 |
| P0 | 招募、筛选、申请、入队、退出、状态 | 多账号真实完成流程且不超员 |
| P0 | 小队群聊、历史、断线补取、权限撤销 | 无重复消息、无退出后继续收取 |
| P0 | 举报、管理员审核、种子数据与启动说明 | 可处理违规并复现演示 |
| P0 | 基于显式条件的推荐与解释 | 不满足硬条件不显示为可直接加入 |
| P1 | AI 招募草稿与缺失项追问 | 真实模型可用，失败可手动完成 |
| P1 | AI 偏好解析与受约束的匹配说明 | 不编造技能、时间和承诺 |
| P1 | 体验打磨、演示脚本、开发证据整理 | 能在干净环境重现关键流程 |
| P2 | 学校真实认证、多校运营、原生 App、小程序 | 首版不实现 |
| P2 | 视频社区、音视频通话、私信、支付、商业化 | 首版不实现 |
| P2 | 复杂任务看板、课表导入、地图规划、长期打卡 | 首版不实现 |
| P2 | 大规模向量检索、自动邀人、自动代用户承诺 | 首版不实现 |

首版支持在资料中选择学校，在全局切换当前浏览学校。默认只显示当前学校内容；招募可显式允许跨校，只有开启“含跨校招募”筛选时才显示其他学校允许跨校的招募。首版试用只推广一所学校，但测试保留第二所虚构学校来验证隔离规则。

## 6 信息架构与页面设计

### 6.1 导航结构

手机端底部导航为“发现、招募、发布、消息、我的”。发现和招募页顶部共享游戏、学习、竞赛、户外四区切换。发现页默认看讨论，招募页默认看队伍。主题页内固定“讨论”和“招募”两个标签，满足用户按具体游戏或其他主题进入的习惯。

桌面端使用左侧导航、中间主内容、右侧条件摘要或队伍摘要，避免简单放大手机布局。界面中文为主，公开文案不展示服务名、数据库名等实现细节。

### 6.2 页面清单

| 页面与路由 | 主要内容 | 关键操作 |
| --- | --- | --- |
| /login 与 /register | 登录、注册、试用账号提示 | 登录、注册、显示错误 |
| /onboarding | 学校、昵称、兴趣与常用时间 | 保存或跳过非必填资料 |
| /discover | 四区、主题、讨论卡片、搜索 | 浏览、筛选、进入详情 |
| /topics/:id | 主题介绍、讨论与招募双标签 | 发帖、发布招募、申请主题 |
| /posts/:id | 图文、作者、评论、关联招募 | 点赞、评论、收藏、举报 |
| /recruitments | 条件筛选、招募卡片 | 查看、比较条件、重置筛选 |
| /recruitments/new | 场景表单、AI 草稿入口 | 保存草稿、预览、发布 |
| /recruitments/:id | 要求、名额、条件对照与状态 | 申请、直接加入、撤回 |
| /teams/:id | 成员、申请、公告、状态与聊天 | 审核、退出、开始、结束 |
| /messages | 小队会话与通知两个标签 | 打开会话、阅读通知 |
| /me 与 /me/edit | 个人资料、我的发布、我的队伍 | 编辑、删除内容、退出登录 |
| /saved | 收藏的帖子与招募 | 取消收藏、进入详情 |
| /admin | 举报、主题申请、用户与内容管理 | 审核、隐藏、封禁、解封 |

### 6.3 核心页面规则

讨论卡片显示主题、标题、最多一张封面、摘要、作者昵称、发布时间和互动数量。采用双列卡片时，移动端仍需保证标题可读；招募列表采用便于比较时间与人数的单列卡片，不强制所有内容都做瀑布流。

招募卡片必须显示区域与主题、开始时间、预计时长、线上或线下、当前人数与总人数、目标、加入方式、状态。竞赛卡片额外显示缺少的角色，游戏卡片显示游戏服务器。已结束或满员卡片不能继续呈现可加入按钮。

小队页将聊天与队伍资料放在同一空间，顶部持续展示状态。申请中用户只能看自己的申请结果，不能读取成员列表中的非公开信息、群公告或群聊。已入队成员可查看队伍成员及公告。

### 6.4 基础交互状态

每个请求页面均需有加载、空数据、失败重试和无权限状态。提交过程中禁用重复按钮；服务端仍需幂等或唯一约束，不能只依靠按钮禁用。网络异常时保留表单草稿；草稿只能包含用户当前填写内容，不保存登录凭据。

首次空社区应显示“还没有相关讨论，发布第一条”，不自动填充看似真实的用户内容。演示数据只在明确标注的演示环境出现。

## 7 账号资料与主题体系

### 7.1 账号与身份

建议默认使用邮箱与密码注册，不接入短信付费服务。首版邮箱为登录标识，不接入真实邮件核验时必须显示“邮箱未验证”，也不能将邮箱域名当作已验证学籍。学校、年级和技能为用户自述。

密码至少10位，最长128位，允许粘贴与密码管理器。昵称2至20个字符，简介不超过300字。默认对外不展示邮箱、账号内部标识、精确课程表、手机号或私人联系方式。可选联系方式只放在成员可见的队伍公告，且不由系统自动索取。

个人资料包含学校、年级可选、兴趣主题、技能标签、技能描述、常用时间及目标偏好。个人主页公开昵称、头像、学校与用户主动公开的兴趣和技能；常用时间默认仅供本人和推荐计算使用，其他人看到的是与当前招募的重叠结论。

### 7.2 角色与权限

平台角色为 USER 和 ADMIN；队伍角色为 CAPTAIN 与 MEMBER，队长不是平台管理员。匿名用户可浏览公开帖子及招募摘要；登录后可发帖、评论、申请或加入。封禁账号不能登录新会话，已存在会话及 Socket 连接应失效。

内容作者只能编辑自己的内容。管理员可以隐藏违规内容、审核主题和处理举报，不能借管理员身份任意加入或浏览私人群聊。处理群聊举报时只展示举报者主动提交且已获成员权限校验的消息证据，所有管理动作记录审计。

### 7.3 主题创建与去重

每个主题属于一个区域，建议首版一个帖子或招募只选择一个主题。游戏区主题示例为无畏契约、怪物猎人等；学习区示例为高等数学、英语四级；竞赛区示例为应用开发、数学建模；户外区示例为城市摄影、徒步。

用户可申请新增主题，填写名称、所属区域和简短说明。服务端对名称进行 Unicode 规范化、首尾空格清理与大小写归一，并维护别名。出现相同标准名称或别名时先展示已有主题，避免“瓦”“无畏契约”等重复分区。

申请状态为 PENDING、APPROVED、REJECTED。管理员批准后形成主题；审核前不能用未批准主题发布内容。主题可停用，但停用不删除历史内容；停止新发布，原内容仍可按权限查看。合并主题作为后续能力，首版可由管理员人工迁移并保留审计。

## 8 讨论社区需求

### 8.1 发帖与互动

帖子包括标题、正文、0至6张图片、主题和可选标签。标题5至60字，正文10至5000字，标签最多5个。正文采用纯文本或受限 Markdown，首版不支持任意 HTML 和脚本。图片只接受 JPEG、PNG、WebP，每张不超过5MB；服务端验证文件实际类型与像素尺寸并重新编码，去除 EXIF 等附带信息。

评论为单层列表，可使用回复引用定位被回复评论，但不实现无限嵌套。每条1至1000字。帖子支持点赞和收藏，分别以用户与目标唯一约束去重；取消操作幂等。首版不开发评论点赞、转发链和复杂关注关系。

### 8.2 讨论与招募关联

作者可从帖子详情发起招募，预填区域、主题并记录 source_post_id。帖子显示作者关联的招募列表，招募详情显示来源帖子。普通读者也可以从帖子发起自己的相关招募，但不冒充原作者，也不修改原帖；关联文案标明“由读者发起”。

首版一个招募最多关联一个来源帖子；一个帖子可关联多个招募。来源帖子被删除或隐藏后，招募仍存在，来源位置显示不可用，不泄露隐藏内容。

### 8.3 排序与搜索

首版提供最新、活跃两个排序。最新按发布时间与ID稳定排序；活跃建议以最近7日评论数为主、点赞数为辅，并在说明中给出规则。不将此描述为个性化 AI 信息流。

搜索覆盖标题、正文、主题名称及招募标题。小数据量先使用 PostgreSQL 参数化 ILIKE 与明确分页，限制查询长度和返回量；中文搜索不依赖默认英文全文分词。出现性能瓶颈后再引入专用检索。

### 8.4 内容状态

帖子和评论状态为 PUBLISHED、HIDDEN、DELETED。作者删除为软删除，管理员隐藏必须有原因。列表不返回隐藏与删除内容，原链接显示相应状态。删除帖子时评论停止新增，收藏关系可保留但列表展示“内容已不可用”。

## 9 招募发布与四区差异

### 9.1 通用字段

| 字段 | 必填性与默认 | 校验与说明 |
| --- | --- | --- |
| 区域与主题 | 必填 | 主题必须有效且属于当前区域 |
| 标题与说明 | 必填 | 标题5至60字，说明20至3000字 |
| 所属学校 | 默认作者学校 | 改学校需本人资料一致，不允许伪造校方身份 |
| 是否接受跨校 | 默认否 | 开启后才进入跨校筛选范围 |
| 线上或线下 | 必填 | 线下必填粗粒度活动地点 |
| 开始与结束时间 | 必填 | 使用具体日期，结束晚于开始 |
| 招募截止时间 | 默认开始时间 | 不晚于开始，发布时晚于当前时间 |
| 队伍总人数 | 必填 | 建议2至20人，包含队长 |
| 加入方式 | 默认申请审核 | AUTO 为符合条件直接加入，APPROVAL 为审核 |
| 活动目标 | 必填 | 如休闲、练习、冲分、复习、参赛或摄影 |
| 必须满足的条件 | 按场景可选 | 每条条件有明确字段、运算与解释 |
| 偏好与备注 | 可选 | 偏好只影响排序，不伪装成准入门槛 |
| 来源帖子 | 可选 | 记录关联，不继承帖子作者权限 |

时间统一存 UTC，页面使用 Asia/Shanghai 显示并注明北京时间。用户输入按页面时区转换，API 使用带时区的 ISO 8601。周期性学习计划首版以明确日期范围和若干具体时段表示，不接入复杂循环日历；单次招募只代表一支队伍。

### 9.2 游戏区

扩展字段：游戏名称来自主题；服务器或大区为必填或明确“不限”；平台为 PC、主机、手机或不限；模式为游戏内玩法；段位范围可选；目标为休闲、练习或冲分；语音偏好为可选。

跨游戏的段位不可直接比较。只有主题配置了顺序枚举时，才允许段位上下限；未知段位不编造数字。服务器若设为硬条件，申请者必须填写相同或在允许集合内的服务器。首版不读取游戏账号、不代登录游戏、不承诺段位真实性。

### 9.3 学习区

扩展字段：科目或考试、具体学习目标、基础水平、自习或讨论或互相讲题、线上会议或线下地点、计划日期内的时段、希望参与频次。基础水平默认软偏好，学习方式由发起人选择是否必须一致。

首版允许发布单次自习和短期复习小组，但不增加签到积分、排行榜、学习资料付费或自动课程表解析。长期学习可由同一小队自行沟通，原招募依然有结束时间。

### 9.4 竞赛区

扩展字段：比赛名称、官方链接可选、项目方向、已有技能、待补岗位、各岗位人数与必需技能、预计每周投入时长、协作时段、比赛截止日期、目标及作品参考链接可选。

队长创建时指定自己占据的岗位，其余空缺按岗位计算。岗位人数之和必须等于总人数，每名成员只占一个岗位。候选人申请时选择岗位；审核和直接加入均检查该岗位剩余名额。首版不实现复杂的同一成员多岗位占用。

技能标签反映自述能力。可填写作品链接和说明作为辅助证据，但平台不进行自动专业能力认证，不用“绝对胜任”作为推荐措辞。合作目标如体验、完成作品、争取获奖为软偏好，不能推断获奖能力。

### 9.5 户外区

扩展字段：活动类型、出发学校或粗粒度区域、集合区域、预算上限、预计路程或时长、活动强度、经验要求、装备要求。预算为每人预计支出，不在平台收取押金与旅行费用。

允许约城市摄影、步行、校园跑步和普通出游。首版围绕低复杂度场景演示，不实现旅游商品交易、保险购买、实时轨迹或向导认证。公开地点与入队后的具体集合说明分开存储并分别授权。

### 9.6 草稿与发布编辑

草稿是作者私有记录，不占名额、不创建群聊。发布时一次性校验完整字段并创建队伍、队长成员关系及群聊，整体事务提交后才对外可见。

发布后标题和非关键说明可编辑，界面显示修改时间。已有其他成员或待处理申请后，学校范围、加入方式、硬条件、时间、岗位数量和总人数锁定；需要变更时应取消并重新发布，避免别人依据旧条件加入。仅有队长且无待处理申请时允许整体编辑，但仍须完整校验。

## 10 入队规则与状态机

### 10.1 条件检查结果

明确条件统一返回 PASS、FAIL、UNKNOWN。硬条件 FAIL 时不能申请或直接加入；UNKNOWN 时要求补充对应字段，不能直接推断通过。软偏好缺失只降低信息完整性，不阻止申请。

自填的学校或技能符合条件仅表示“按自述资料符合”，界面不得显示“学校已认证”“能力已认证”。服务器、学校范围、岗位、时间可用性等硬条件应展示具体依据，不能只显示笼统分数。

### 10.2 申请与直接加入

AUTO 模式下，用户显式点击加入，服务端在事务中重新检查账号、条件、时间、容量和岗位，成功后立即获得成员权限。APPROVAL 模式下先创建 PENDING 申请，队长批准时执行相同检查，批准成功才占名额并进群。

待审核申请不占名额。申请达到满员之前提交、满员之后才被审核时，批准返回无名额，不产生半加入状态。建议同一招募待审核申请最多100条，同一用户同时待审核申请最多10条；限制可配置，避免无上限骚扰。

申请状态为 PENDING、APPROVED、REJECTED、WITHDRAWN、EXPIRED。重复申请返回当前有效申请；拒绝或撤回后允许在10分钟后重新申请，成员被移除后首版不允许再次加入该队。招募关闭时未处理申请统一变为 EXPIRED，并通知申请者。

### 10.3 队伍状态

| 状态 | 进入条件 | 可加入或申请 | 群聊权限 |
| --- | --- | --- | --- |
| OPEN | 已发布且仍有名额、截止未到 | 可按加入方式处理 | 当前成员可读写 |
| FULL | 人数达到总人数、截止未到 | 不新增申请与成员 | 当前成员可读写 |
| IN_PROGRESS | 队长开始且人数至少2人 | 不再招人 | 当前成员可读写 |
| COMPLETED | 队长结束活动 | 不可 | 成员只读归档 |
| CANCELLED | 队长或管理员取消 | 不可 | 成员只读归档 |
| EXPIRED | 截止已到且未开始 | 不可 | 成员只读归档 |

允许的主要转换：OPEN 与 FULL 根据当前有效成员数互相转换；OPEN 或 FULL 可开始进入 IN_PROGRESS；IN_PROGRESS 可结束进入 COMPLETED；OPEN、FULL、IN_PROGRESS 可取消进入 CANCELLED；OPEN 或 FULL 到招募截止时间进入 EXPIRED。终态不允许重新打开；需要继续招募时复制为新草稿。

FULL 不自动开始，人数凑齐后仍由队长确认。OPEN 状态至少2名有效成员即可开始，允许未满员先开展。到开始时间仍未操作时，因默认截止时间不晚于开始时间，应进入 EXPIRED；页面不能自动把未确认活动当作已进行。

定时任务每分钟处理过期状态；所有加入、批准、开始、发消息等入口在执行前同样检查时间，防止任务延迟产生可加入窗口。进程重启后扫描待处理队伍；不能只依赖进程内定时器计时而忽略数据库时间。

### 10.4 退出 移除与队长转移

OPEN、FULL、IN_PROGRESS 中普通成员可主动退出，队长可移除成员并记录原因。退出或移除立即撤销群聊读写权限，服务端将该用户所有连接移出房间。招募中的空位可恢复，但 IN_PROGRESS 不重新开放招募。

队长不能直接退出造成无负责人队伍。必须先把队长身份转交给现有成员，或取消队伍。转交必须使用队伍事务锁并记录系统消息；队长原岗位不随身份转移而改变。队伍终态不再变更队长。

建议默认：成员主动退出或被移除后，该队伍首版不再允许其重新入队，避免历史权限区间处理失控。若后续要支持重新加入，应先引入成员任期和按任期可见的消息策略。

### 10.5 名额与并发

每次加入、批准、退出、移除、转交、开始或取消均锁定同一队伍记录，再检查并更新关联数据。采用 PostgreSQL 行锁或经验证的等价原子方案，禁止仅在前端判断人数。岗位名额与总人数必须在同一事务内成立。

建议使用有效成员记录实时计数作为人数依据，队伍上可保留缓存字段但不得成为未经校验的唯一事实。发布事务保证招募、队伍、队长和聊天空间同时存在或同时回滚。事务提交之后才发送 Socket 事件和通知，避免广播未提交状态。

## 11 临时小队群聊

### 11.1 功能范围

首版提供文字消息、系统消息、队伍公告、历史分页与未读数量。文字每条1至2000字，按用户与队伍限速；不提供语音、视频、文件发送、私信、阅后即焚和复杂已读回执。

队伍与群聊一对一。成员入队后进入队伍页；聊天不是公开聊天室。队伍公告只允许队长编辑，活动具体集合点属于公告的成员可见字段。

### 11.2 消息持久化与幂等

客户端每次发送生成 client_message_id。服务端检查会话与当前成员权限，在数据库保存消息后返回正式 message_id 与队内递增 seq，再广播。唯一约束为 team_id、sender_id、client_message_id，重试返回原消息，不再创建新记录。

队内 seq 使用原子计数分配，不能用时间戳或随机 UUID 作为先后依据。客户端按 seq 排序并按 message_id 去重，收到序号缺口时补拉历史。未收到确认的消息显示发送中或失败，可手动重试；不能直接显示为服务端已保存。

Socket.IO 默认并不保证所有消息一定送达，应用必须自行持久化并补取。首版以 HTTP 拉取为事实来源、Socket 为及时通知通道，网络重连后主动同步遗漏消息，不依赖库的默认行为声称零丢失。

### 11.3 连接与补取

Socket 握手使用与 HTTP 相同的有效会话。客户端请求订阅队伍时，服务端查询成员资格，不能信任客户端传来的 user_id。每次发消息再次验证成员、封禁和队伍状态。

重连或页面重新可见时，客户端携带 last_seq，通过 HTTP 查询该队之后的消息；若返回 more 则继续分页。正常连接下也进行低频同步以弥补提交成功但广播失败的窗口。新成员默认可读该队现有全部聊天历史，加入前在详情提示；首版不支持加入前历史隔离。

退出、移除、封禁、会话注销必须使全部关联连接失效或离开受保护房间。读取历史、获取公告、订阅和发送均独立鉴权；只移除页面入口不能代替服务端撤权。

### 11.4 归档与数据期限

队伍进入终态后，仍在成员名单中的成员可只读查看。建议默认归档30天，之后隐藏并删除聊天正文与成员专属公告；招募公开摘要可保留，成员关系仅保留维护队伍记录所需的最少字段。开发与演示环境可配置较短期限验证任务。

历史中已软删除的消息保留 seq 和占位状态，不返回原文。读取接口独立检查 archive_until，归档到期即拒绝返回正文，不能因清理任务延迟继续暴露数据。正文删除需同时处理在线缓存与后续备份轮换；备份建议保留7天，恢复后重跑到期删除任务。记录这些期限为产品建议，正式上线前应结合实际用途确定并对用户说明。

## 12 匹配与推荐设计

### 12.1 匹配对象

首版支持两种视图：参与者查看“适合我的招募”；队长查看“申请者与岗位的条件对照”。不对全校用户开展无授权的人肉搜索，不自动邀请未申请的陌生人。队长仅对自己队伍的申请者获得匹配建议。

“招募匹配”首先是大厅筛选与条件对照；自动推荐为辅助。用户始终可手动搜索和查看，不需要先完成长问卷。

### 12.2 规则顺序

第一层检查招募是否可加入、学校范围、账号状态、岗位空缺、具体时间、场景必需条件。第二层只对没有硬条件冲突的候选计算软偏好适配。第三层给出依据和信息缺口，最后由用户决定申请、队长决定批准。

硬条件缺失应标为待补充，不参与“可直接加入”推荐；可在独立分组显示“补全资料后可判断”。推荐排序不得通过较高软分覆盖硬条件不满足。

### 12.3 首版评分方法

使用可配置的加权评分作为排序工具，不把分数解释为成功概率。建议四维权重：时间适配35、目标一致25、场景偏好20、技能或经验适配20。游戏的最后一维可映射玩法或段位偏好；学习映射基础或方式；户外映射经验或强度；竞赛映射岗位所需技能。

对每项返回适配值0至1、证据与信息状态。已知且适用的维度进入分母，缺失维度单独计入资料完整度；适配分为100乘以已知维度加权适配和，再除以已知维度权重和。所有维度未知时返回空分值，不返回0或100。界面同时展示“已确认条件”与“尚未确认”，避免少量信息得到高分后误导。

确定性基线优先使用明确枚举、标签与时段。时间适配按候选可用时段覆盖招募要求的比例计算，重叠分钟与招募要求分钟之比最大为1；若设为硬条件，默认需要覆盖全部要求时段。目标一致采用相同枚举为1、经配置的兼容目标为0.5、冲突为0。技能适配按岗位必需技能命中比例，声明为硬技能时必须全部满足，否则只能提示缺口。

“不限”的维度不参与评分。候选时间未填写为未知，明确无空为不满足。时间只针对当前活动日期展开，不能把每周空闲误当成当天一定可用；页面要求用户确认本次时间可用性。

### 12.4 解释示例

竞赛申请者的说明可以是：“你选择了前端岗位，资料中填写了 Vue 和界面开发经历；周二、周四晚与当前计划一致。你尚未填写每周能投入多少小时，请在申请前确认。”

禁止把未填写的经历补成“丰富项目经验”，禁止声称一定能获奖，禁止依据聊天推断心理特征并用于排名。首版不基于性别、家庭、经济状况等非必要属性形成隐性分数。

## 13 AI 功能规格

### 13.1 AI 招募草稿

用户从发布页选择“用一句话描述”，输入不超过2000字的需求。AI 返回符合 JSON Schema 的结构化草稿、缺失问题、来源依据和不确定字段。前端显示生成预览，用户确认并补全后才允许发布。

输出键建议为 category、topic_suggestion、title、description、time_candidates、capacity、join_mode、hard_constraints、preferences、category_details、missing_questions、uncertain_fields。每个推断字段附 source_excerpt 或明确 assumption，不能把默认假设伪装成用户原话。

模型可建议“时间待确认”，不得自行决定日期、预算、人数、参赛目标或岗位承诺。用户说“今晚”时，服务端向模型提供当前北京时间，若当天日期解释仍有歧义，应要求用户确认具体时间。发布接口只接收已确认的正式字段，不直接接受未校验模型输出。

### 13.2 AI 匹配说明

模型输入仅包括当前招募必要字段、用户主动提供的相关资料和规则层生成的证据清单。候选排序与硬条件结果先由规则确定。模型可以将证据改写成清楚的说明，或把“轻松玩、不压力”等偏好映射为待确认标签，不能篡改名额、服务器和硬条件结论。

每个解释句应能追溯到输入字段或证据ID。结构校验失败、出现未知技能或前后矛盾时丢弃该说明，显示规则模板。首版不要求向量数据库、模型微调或读取全量群聊。

### 13.3 调用与降级

服务端使用单独模型适配器，提供 generateRecruitmentDraft 和 explainMatch 两个方法。API Key、模型名、服务地址和超时放在服务端环境变量，浏览器永远不直接持有密钥。模型服务商在 D1 根据实际可访问性、数据要求和预算确定，前端不绑定品牌。

建议超时20秒，单次最多自动重试1次，仅对可重试错误且未成功返回时执行；采用请求幂等记录避免无意重复计费。建议默认每个用户每天最多10次招募生成、20次解释，管理员可配置总预算开关。实际费用依据调用日志和当时服务商价格核算，本文不提供未经核实的固定报价。

模式必须明确区分 LIVE、RULES_ONLY、DEMO_FIXTURE。LIVE 才代表真实模型调用；RULES_ONLY 在界面提示“当前使用条件规则”；DEMO_FIXTURE 仅用于可重复测试并在演示环境显著标注，不能录制为真实智能效果。模型失败时保留输入并回到普通表单。

### 13.4 输入与输出安全

招募文本、帖子与技能描述属于不可信数据，系统指令与用户文本分离。模型不具备发帖、批准申请、删除数据、调用支付或读取任意网址的工具权限。输出只通过受限结构进入草稿，不执行代码与链接。

测试至少包含时间未明确、预算缺失、互相冲突条件、恶意指令、超长文本、服务超时、非 JSON 输出、虚构技能说明8类情况。AI 功能不因表现不稳定而拖垮基本招募流程。

## 14 技术架构与工程选择

### 14.1 建议默认技术路线

| 层级 | 建议方案 | 选用理由与限制 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 页面与状态清晰，适合 Web 原型到可用应用 |

### 14.2 结构与边界

前端通过 /api/v1 访问 HTTP，通过 /socket.io 访问实时服务。生产建议由同一域名反向代理到应用；开发由 Vite 代理到服务端，使 Cookie 与 Socket 权限处理尽量一致。API、任务和 Socket 在首版单服务进程中运行，数据库是共同事实来源。

推荐仓库目录如下，路径表示建议产物而非当前已经存在的应用：

- apps/web：页面、组件、路由、表单与客户端数据请求。
- apps/server：HTTP、Socket、鉴权、定时任务与业务服务。
- packages/contracts：Zod Schema、DTO、错误码和枚举。
- packages/matching：纯规则匹配与可重复测试。
- prisma：数据结构、迁移与种子脚本，按所选 Prisma 版本组织。
- docs：本项目书、接口说明、架构决策、开发过程与验收记录。
- tests/e2e：多人场景与浏览器端到端测试。
- infra：Compose、反向代理和部署说明。

模块边界为 auth、profiles、topics、posts、recruitments、teams、chat、matching、ai、moderation。HTTP 和 Socket 共用 service 层权限与事务逻辑，禁止分别维护两套入队和发消息规则。

### 14.3 文件与图片

首版图片保存到服务端持久化目录，以随机文件名存储，不允许用户指定磁盘路径。公开帖子图片可公开读取；成员专属附件首版不提供。生产部署需挂载持久卷并纳入备份；后续可替换为对象存储适配器。

上传先形成临时记录，发布内容后绑定；未绑定图片24小时后清理，作者不能绑定其他用户临时图片。正文隐藏后图片访问策略同步处理，不能只隐藏HTML链接而继续暴露敏感内容。

### 14.4 部署路线

本地先完成数据库与前后端运行，再在普通可运行 Node HTTP 与 WebSocket 的主机部署。需要长连接支持，不能未经验证把服务端直接放到只支持短函数请求的平台。实际云平台、域名与付费资源由负责人另行选择，本文不默认购买或公开发布。

## 15 数据模型与约束

### 15.1 通用规范

业务ID采用 UUID，聊天队内序号采用 bigint。时间字段使用 timestamptz，金额预算用整数分，时长用分钟，避免浮点与无单位字段。通用 created_at、updated_at 由服务端维护；可删除内容保留 deleted_at。JSONB 仅保存场景扩展和模型结果，核心名额、成员及权限使用关系表。

以下是实现级逻辑模型。Codex 应形成完整迁移与类型，不得将整个业务压缩成一张 JSON 表。数据库实体采用单数或复数命名均可，但全仓一致。

| reports | id、reporter_id、target_type、target_id、reason、evidence_json、status、handler_id、handled_at | 目标需存在；群聊证据需验证举报人权限 |

### 15.5 事务不变量

- 一个已发布招募恰好对应一个队伍与一个聊天空间；草稿不对应队伍。
- 有效成员数始终小于等于队伍容量，岗位有效成员数不超过岗位容量。
- 队长恰好一人且为有效成员；总人数包含队长。
- 批准申请、创建成员、变更状态及记录系统事件全部成功或全部回滚。
- 入队后方可读写聊天；待审核申请不授予成员权限。
- 消息先保存后确认，重试不重复，seq在队内唯一递增。
- 封禁、移除与退出后的读取和发送均被服务端拒绝。

## 16 HTTP 接口契约

### 16.1 通用约定

接口前缀 /api/v1，JSON 使用 camelCase，时间为 ISO 8601，bigint 序号在JSON中用十进制字符串。成功返回 data 与可选 meta；失败返回 error.code、error.message、error.fields 和 requestId。状态码区分400格式错误、401未登录、403无权限、404不存在或不可见、409状态冲突、422业务条件不满足、429限流与503服务暂不可用。

列表默认20条，最大50条，使用 createdAt与ID组成的不透明游标。消息使用seq游标。错误码必须稳定，不用中文文案作为前端业务判断条件。Cookie之外的身份字段不由客户端指定，服务端从会话取得当前用户。

所有变更请求使用同源检查与CSRF令牌；登录后的操作同时要求有效会话Cookie。注册与登录前先获取匿名CSRF上下文，成功登录后轮换会话与令牌。重复操作按业务唯一约束幂等；发布招募等创建请求支持 Idempotency-Key，保存请求摘要与结果，重复键不同请求体返回409。使用 request_keys 表实现通用24小时幂等缓存，唯一范围为用户与路由及键。

2026-10-19 首周讨论实现修正：`POST /posts` 使用请求体 `requestKey: UUID`，在 Post 保存作者范围内唯一标识与规范化内容摘要，不增加通用 request_keys 表。记录随帖子保留；旧记录元数据可空。相同请求重试返回原帖当前可见版本，同键不同内容 409，已隐藏 / 删除 410，不能通过重试恢复。浏览器保留本页提交标识并锁定结果未知的输入，明确校验拒绝后才解锁；关闭 / 刷新页面不保证恢复。招募沿用已实现的请求体 requestKey 与发布幂等契约；未实现路由不据此计为完成，详见 DECISIONS.md 与 API.md。

2026-10-20 招募创建实现修正：请求体契约不变，新增独立 RecruitmentCreateRequest 保存作者范围唯一键、摘要、时间和可空草稿关联。创建与关联同事务，既有数据回填；删除草稿后关联为空，原键重试 410，不能复建。该最小记录无自动 24 小时过期，账号硬删除时级联清理；不包含草稿正文，也不新增账号删除功能。浏览器固定未确认创建的快照，后续修改先找回原创建，再按初始 revision 保存；他页更新 / 发布时停止恢复写入并保留本地输入，避免静默覆盖。

## 17 Socket 事件与通知

### 17.1 事件契约

| 方向与事件 | 主要载荷 | 处理要求 |
| --- | --- | --- |
| 客户端 team:subscribe | teamId、lastSeq | 服务端验成员后加入房间并ack |
| 客户端 team:unsubscribe | teamId | 仅退出订阅，不代表退出队伍 |
| 服务端 message:created | teamId、messageId、seq、type、body、createdAt | 数据库提交后发送，客户端去重 |
| 服务端 team:updated | teamId、status、memberCount、version | 更新摘要，必要时重新取详情 |
| 服务端 membership:revoked | teamId、reason | 清受保护缓存并离开界面 |
| 服务端 notification:created | notificationId、type、entityId | 只发给该用户所有有效连接 |
| 服务端 session:revoked | reason | 清登录态并断开 |

所有事件包含 eventId、occurredAt 和 schemaVersion，team:updated 的 version 在事务内递增，避免旧事件覆盖新状态。teams表补充 version 字段。事件不是权限证明；收到事件后拉取接口仍要鉴权。

### 17.2 通知触发

通知包括新申请、申请通过或拒绝、招募关闭、队伍开始或结束、被移除、队长转交、主题审核结果。首版只有站内通知，不发短信邮件，不设置后台自动外部联系。

聊天未读按成员 last_read_seq 与最新可见 seq 计算，不能把所有系统事件都计成多条提醒。退出和移除后不再收到该队通知。通知载荷只存必要摘要，不复制私人聊天全文。

### 17.3 可靠性边界

事务提交后若广播失败，数据库状态仍是正确结果。客户端通过重连、页面重新可见与低频补取恢复；通知列表持久化，不因Socket断开消失。首版不引入消息队列，接受短暂通知延迟，不能接受数据库已成功但前端永久丢失记录。

## 18 匹配输入输出与示例

### 18.1 统一条件结构

每条条件包含 field、operator、value、severity、label 和来源。severity 为 HARD 或 SOFT；operator 限于 equals、in、range、containsAll、timeCovers 等枚举，服务端按区域白名单解释，禁止执行任意表达式。

条件检查结果包含 code、status、expected、actualSummary、missingFields 和 evidenceIds。公开结果不输出他人的完整可用时间表或私人资料。匹配结果包含 eligible、fitScore可空、informationCoverage、matchedReasons、conflicts、unknowns 和 scoringVersion。

### 18.2 竞赛招募样例

样例为演示数据，不指代实际报名团队：队伍总人数3人，队长占“后端”1人，另有“前端”1人和“设计”1人；每周二、四19点至21点协作；目标为完成可演示作品；加入方式为审核。

候选A自述具备前端技能并确认全部协作时间，申请前端岗位，系统显示岗位技能与时间符合。候选B只有设计兴趣且周四不能参加，申请前端岗位；若时间为硬条件，则明确列出冲突，不能直接提交申请。候选C没有填写可用时间，显示资料待补全，不因兴趣相同显示高可信匹配。

前端岗位通过A之后，另一位申请同岗位的用户即使已在等待，也不能继续被批准。设计岗位仍有空时队伍总状态仍为OPEN，但前端岗位显示已满。

### 18.3 游戏招募样例

总人数5人，PC平台、指定服务器、今晚20点至22点、休闲模式、AUTO加入。用户资料服务器不同返回硬冲突，时间未知要求确认，全部满足后才能加入。第五个位置被两人同时点击时，事务只允许一人成功，另一人得到TEAM_FULL并刷新状态。

## 19 安全 隐私与基础运营

### 19.1 身份与权限

服务端会话token采用安全随机值，数据库仅存摘要。Cookie启用HttpOnly，生产启用Secure与合适的SameSite设置；Session建议有效7天，可随时撤销。密码使用成熟库进行Argon2id或经评估的bcrypt摘要，算法参数与升级方式写入架构记录，不自研密码算法。

所有修改请求校验CSRF与Origin。Socket握手校验允许的Origin，并验证有效Session；后台任务和API同样检查封禁状态。不能仅因为前端隐藏按钮就认为权限安全。

### 19.2 输入与文件

API统一Schema校验并拒绝未支持字段，数据库查询参数化。上传校验实际字节、文件类型、像素及配额，拒绝SVG、可执行文件和路径穿越。用户输入按文本渲染，外链添加安全属性，禁止危险协议。

速率限制至少覆盖登录、注册、发帖、评论、入队、聊天和AI。单实例先使用内存限流加数据库持久化配额；进程重启可能重置短期窗口，需要在部署说明中说明。未来扩到多实例时再引入共享限流与Socket适配器。

### 19.3 个人资料最小化

不收集身份证、学籍证明、人脸、支付信息和实时定位。学校身份明确为自述。对外不暴露邮箱、私人空闲表和AI请求原文。日常日志不记录密码、Cookie、token、密钥和完整聊天正文。

首版在个人页提供数据与隐私说明和删除申请入口；管理员依申请撤销会话、匿名化公开作者信息、删除资料和可删除正文，同时记录处理结果。自动化自助导出与删除可列入后续，但试用阶段仍须有实际可操作的处理办法。

### 19.4 内容治理

举报原因包括广告、骚扰、欺诈、侵犯隐私和其他。管理员可隐藏内容、取消招募、临时封禁用户；处理时填写原因并通知当事人。首版不引入不透明的社会信用分和自动永久封号。

被封禁队长的招募中或进行中队伍应取消并通知成员，避免出现无人管理的有效队伍。管理员不能把其他人强行转为队长。举报功能用于最低限度的试用治理，不代表已完成面向大规模公开运营的全部准备。

## 20 质量目标与测试方案

### 20.1 非功能目标

以下均为目标值，必须在明确测试环境下实测后报告，不能当作已实现性能：390像素手机视口与1440像素桌面视口均可使用；普通列表API在本地或单机测试环境、50个并发请求场景下P95不超过800毫秒；聊天在本地稳定网络下提交到第二客户端可见P95不超过1秒，不含AI请求；AI结果超过20秒进入失败回退。

首版不承诺大型社区并发或全天候可用率。性能报告记录机器、数据库数据量、请求类型、并发方式与异常比例。界面支持键盘访问、可辨认焦点、输入标签、错误提示与足够对比度，图片有替代文本或明确装饰属性。

### 20.2 测试分层

规则单元测试覆盖硬条件PASS、FAIL、UNKNOWN，评分缺失分母、时间重叠、岗位适配、状态转换和输入校验。API集成测试使用独立PostgreSQL测试库，验证真实约束、事务回滚与权限，不能全部用内存mock替代数据库行为。

端到端测试使用至少三个独立浏览器上下文，对应队长、申请人和旁观者，验证界面、Cookie和Socket权限。AI测试分为可重复的固定样例测试与人工执行的真实模型冒烟，固定样例不能被计为模型真实成功。

### 20.3 必须覆盖的高风险场景

- 两人争抢最后名额、两人争抢同一岗位、重复点击批准，均不得超员或重复入队。
- 发布时中途失败，数据库不得留下没有队伍的公开招募或孤立聊天空间。
- 待审核用户和知道teamId的旁观者不能订阅或读取聊天。
- 成员退出、被移除、封禁或注销后，已有Socket连接同样失去权限。
- 消息保存成功但响应丢失，使用相同client_message_id重试只能得到原消息。
- 断网期间其他人发送消息，重连后按seq补齐并保持顺序。
- 截止瞬间入队、进程重启后过期清理、任务延迟时的API校验正确。
- 队长不能直接退出；转交、取消与退出并发时只发生合法结果。
- 软删除、隐藏、撤销图片与来源帖不可见时不泄露原内容。
- AI超时、限额、错误结构和恶意输入不阻断普通表单发布。

先取消复杂动效、活跃排序和非必要标签；其次减少封面变化、扩展过滤器与收藏便利功能，但要同步调整验收并记录原因。四区可以共用组件和默认岗位，不能通过删除其中三区来冒称完整实现原构想。

优先保留登录、四区浏览、基本发帖、招募、申请审核、群聊、权限与AI实际可用的一项核心增强。若只能完成较小版本，应如实说明范围，更新本文优先级和验收表，不把未实现按钮作为功能展示。

### 22.3 个人学习目标

开发者应能解释一个发布请求如何写入数据库，为什么批准申请需要事务，Socket为何要再次鉴权，模型输出为什么不能直接发布，以及一次失败如何通过日志定位。每阶段整理一张实际数据流说明或一次Bug复盘，为答辩提供可理解的工程证据。

| 指标 | 定义 | 使用方式 |
| --- | --- | --- |
| 招募发布耗时 | 从打开发布页至成功发布的时间 | 对比手填与AI草稿，标明样本量 |
| 申请完成率 | 成功提交申请人数除以开始申请人数 | 分析表单与条件提示是否清楚 |
| 条件理解正确率 | 用户能否正确说出时间、名额、目标 | 验证卡片与详情信息组织 |
| 组队完成率 | 测试任务中达到约定人数的队伍比例 | 受样本招募供给影响，不能直接外推 |
| AI字段准确性 | 人工标注下正确提取字段数与应提取字段数 | 缺失与虚构分开统计 |
| 推荐可解释性 | 用户能否说出推荐依据与未知项 | 避免只调查喜不喜欢界面 |
| 故障情况 | 超员、越权、丢失、AI失败与恢复记录 | 展示工程鲁棒性 |

小样本只能说明当前试用表现。不能把10人任务测试外推为全校普及率、长期留存或商业市场规模。初始目标为所有参与者能完成核心流程，具体效果改善幅度在实测后填写。

## 25 资源 风险与参考

### 25.1 所需资源

一台能运行浏览器、Node和PostgreSQL的电脑即可开发；现有电脑性能足以承担此类应用的常规开发，首版无需本地部署大模型。使用Docker前应确认Windows虚拟化与可用环境，已有PostgreSQL也可直接接入，但README必须说明一条清晰默认路径。

成本分为AI编程订阅、应用内模型调用、演示主机、域名与存储。已有订阅是否覆盖应用内API调用需按实际服务规则确认，不能默认互通。建议负责人先设一个可承受的总预算上限，开发默认使用本地环境和受控模型配额，部署前记录当期报价再决定。

### 25.2 风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 范围过大 | 页面很多但流程无法走通 | 先实现一条真实竞赛组队，再复用到三区 |
| 过度依赖AI编码 | 能生成代码却解释不清状态 | 每阶段记录数据流，关键服务加集成测试 |
| 创新表达不足 | 介绍停留在校园版内容社区 | 展示场景条件、互补岗位与实际试用证据 |
| 实时权限漏洞 | 退出后仍收到消息 | HTTP与Socket共用鉴权、全连接撤权测试 |
| 并发与数据错误 | 超员、重复成员、半发布 | 队伍锁、事务、唯一约束与幂等 |
| AI服务不可用 | 超时、额度不足、输出不稳定 | 规则与手动流程常驻，真实模式如实标注 |
| 校园冷启动 | 内容空、招募无人响应 | 小范围定向试用，避免伪造活跃用户 |

## 26 Codex 启动与执行指令

### 26.1 交接方式

在目标电脑新建项目目录，把本Markdown文件放到docs/PROJECT_SPEC.md，并将单独的CODEX_START.md放在仓库根目录。Word版用于阅读和评审，Markdown版作为开发时的事实基线。先向Codex提供下述启动指令，再逐里程碑推进。

本项目书是开发输入，不意味着已经创建应用。Codex应首先检查工作目录及现有代码，遵守现有仓库规则；若目录已有项目，应先说明可复用部分与冲突，不能直接覆盖用户代码。

### 26.2 可直接粘贴的启动指令

请完整阅读docs/PROJECT_SPEC.md，按其中v1.0基线开发校园兴趣社区与智能组队平台。保留游戏、学习、竞赛、户外四区，以及每区的讨论与招募双板块。以竞赛组队为第一条完整流程，再复用至其他三区。

先检查当前环境、现有仓库规则、依赖与数据库可用性，形成短计划后立即执行M0。采用本文建议技术路线；版本兼容问题先验证并记录，不使用过期API拼接。创建README、.env.example、锁文件、迁移与种子脚本，以及docs/DECISIONS.md和docs/PROGRESS.md。

第一轮只完成M0与最小数据库连接验证，不一次性生成全部页面。随后按M1至M6执行；每一阶段实现真实API与持久化，运行相关检查，更新进度并汇报实际结果。核心功能不能用localStorage、静态数组和假Socket代替，测试固定数据必须与运行环境区分。

重点保证总人数含队长、待审核不占位、批准时重查、岗位名额、队伍事务锁、消息幂等、重连补取、退出撤权，以及AI失败后手动流程可用。不要自行增加支付、原生App、音视频、复杂社交关系或实时定位。

涉及普通可逆实现选择时按本文默认推进；若存在直接影响范围、预算、真实身份认证或公开部署的决定，先列出具体影响再由负责人决定。不得伪造测试、AI调用、认证、用户量、试用反馈和性能结果。
