## 开始编码前统一的规则

这些是下一周的验收约束，实施时同步 [决策](../DECISIONS.md)、共享契约、迁移和接口；当前 API 没有这些能力。

1. 条件对照使用实际身份学校、账号状态、截止、岗位和当次时间确认。浏览筛选的学校不能替代身份学校；自由文本时段不能自动推断相容；技能仅为自述，不显示认证或总匹配百分比。缺失硬条件 UNKNOWN 要求补充，明确 FAIL 拒绝申请。
2. 申请保存所选岗位、当次说明 / 时间确认、必要规则版本与依据。一个用户同队只有一条申请身份；PENDING 不占位。拒绝 / 撤回后按规格的 10 分钟冷却再申请；待审核上限每队 100、每人 10，在事务中检查。
3. 所有成员 / 申请写入共用固定顺序的招募和队伍行锁；批准重查实时资料、规则和总量 / 岗位。不能用前端条件结果当凭据。队长占总人数一个岗位，每人一个岗位；FULL 不新增申请，保留原待审，批准仍重查空位。
4. 活动状态与实时招募状态分离；W2-01 明确旧 TeamStatus 的迁移映射，不能把 OPEN / FULL 同时当活动阶段和招募开关。截止停止申请 / 批准：至少两位有效成员可待开始，不足两位过期；开始须在计划起止时间内且至少两人，关闭 / 开始使剩余待审失效并留通知。
5. 成员退出 / 移除、申请结果、通知和 DomainEvent 同事务提交；通知页面以 HTTP 数据为准，本周不实现 Socket 推送。被移除者不得再次申请同队；队长直接退出被拒绝，转交或取消留在后续完善，不开放造成无队长的操作。
6. 申请中用户只看本人申请，队长只审核自己队伍。成员视图与非公开申请采用独立服务端权限；公开招募的总人数不等于获得成员资料权限。没有消息服务时不显示可用群聊入口。
7. 发布后关键字段目前只读的限制继续保留，不在有申请后顺便开放修改条件。请求重试不能重复批准、恢复撤回或重新加入；明确冲突时保留本页说明，让用户核对当前状态。
