# CampusTogether 开发计划书

版本：v1.1　编制日期：2026年10月15日　执行方式：个人开发，AI辅助编程，每周滚动规划

**本项目以校园兴趣社区与可解释组队平台为目标，每7天形成一次可验收交付，第7天总结并制定下一周计划。** 每周投入30—40小时；当前只锁定首周任务，后续周只设方向和阶段门槛。根据实际完成情况调整任务，不提前承诺整个月每天的工作。

产品保留游戏、学习、竞赛、户外四区，每区具有讨论和招募。竞赛组队承担重点展示：自然语言生成招募草稿，明确时间和岗位，解释条件，人工审核，入队协作。首版为手机优先的响应式Web应用。

## 产品交付的主线

一个用户注册并完善最少资料，在主题中发布讨论并发起招募；系统检查条件并展示信息缺口；其他用户主动申请或加入；队长审核后成员获得群聊权限；队伍停止招募、开始活动并结束归档。

完整参赛版本的主要交付包括：真实账号和资料、四区讨论与场景招募、竞赛岗位、申请与成员、多人文字群聊、规则条件对照、AI草稿与受约束解释、基础举报管理、持久化通知、可复现启动、必要测试和实际开发记录。

支付、音视频、实时定位、原生App、复杂积分、自动邀请和多校运营不进入当前开发。收藏便利功能、活跃排序、复杂别名管理等若挤占核心流程，在周复盘中决定是否后移，并同步范围文档。

## 每周如何推进

每周先确认一个可演示的用户结果，再拆任务；必须完成任务计划占可用时间约70%，联调与缺陷约20%，复盘和证据整理约10%。30—40小时是容量上限，不是要求把所有小时排满。

每个任务需要记录：编号、要完成的用户行为、前置依赖、预计投入、验收步骤、实际证据、状态和遗留问题。状态采用待开始、进行中、待验收、已完成、阻塞。单人同一时段集中处理一条主要业务流程。

| 周内时段 | 工作方式 | 当日留下什么 |
| --- | --- | --- |
| 第1天 | 根据上周结果确认本周承诺，澄清产品和接口边界 | 本周任务与验收条件 |
| 第2至5天 | 按小步骤实现、验证和提交，持续联调 | 实际提交、检查结果、关键Prompt链 |
| 第6天 | 集成演示、权限与失败场景检查，修复阻断问题 | 演示步骤、缺陷清单、已知限制 |
| 第7天 | 验收、总结、校准剩余工作量并编写下周计划 | 周总结、证据索引和下一周任务 |

每天留10—15分钟更新实际进度。Prompt记录保留必要上下文、AI建议、人的取舍、代码变化和验证结果；重要内容不依赖事后回忆补写。功能达到可验收的小节点后提交Git，不将整个应用一次性提交。

第7天复盘建议用3小时左右：约60分钟演示和验收，45分钟整理缺陷与过程证据，45分钟安排下一周，30分钟留给修正和确认。具体时间由实际进度调整。

未完成任务分成：必须先解决的阻断问题、影响当前流程的缺陷、可以延期的增强。下一周先处理前两类，再决定新任务；不把所有遗留工作直接叠加到原计划上。

## 需要在对应模块开始前落实的规则

1. **招募状态与活动状态分开。** 招募截止只停止新申请和批准。截止时已有至少2名有效成员的队伍保持待开始；不足2人则过期。活动在计划开始时刻至结束时刻之间可由队长开始，不再以招募截止作为开始权限条件；未开始且超过计划结束时间则过期。已开始活动超过预计结束时刻时提示队长结束，不自动宣称活动已经完成。
2. **满员与申请。** 总人数包含队长，待审核不占位。FULL时不新增申请，已有待审核可保留；真正关闭招募或开始活动时，剩余申请失效并留下通知。批准必须重查容量、岗位、账号和条件。
3. **本次条件确认独立保存。** 申请和直接加入请求带场景化回答与本次时间确认；区分长期资料与临时确认，保留必要规则版本和依据。资料仍为自述，不能显示认证能力。
4. **统一事务和落库时机。** 入队、退出、批准、转交和状态变更共用队伍事务边界。对应站内通知或可恢复的待通知事件一同落库；Socket推送在提交后执行。
5. **条件对照先于推荐。** 基础PASS、FAIL、UNKNOWN与岗位、时间校验随第2周组队实现。首版UI优先展示依据和缺失项；信息不齐不显示误导性的总匹配百分比，软排序后续校准。
6. **聊天权限以服务端为准。** HTTP保存并持久化，Socket通知，消息幂等和seq补取。退出、移除、封禁、注销撤销已有连接权限；已接收的历史数据不能声称可从他人设备远程抹除。
7. **AI只给草稿和解释。** 用户确认后发布，模型不代替入队或批准；整个请求使用明确时间预算，模型失败保留输入并回到手填。LIVE、规则模式和测试样例明确区分。
8. **删除和学校边界。** 删除队长账号前处理队伍负责人或取消；浏览学校筛选不等于用户学校身份；跨校访问和加入分别校验。

上述属于本计划的设计默认，实施时统一同步状态机、数据迁移、接口和验收案例，不同时保留两套冲突规则。

## UI交付方式

统一采用《UI设计语言规范》v1.2 新粗野主义方向，见 docs/UI_DESIGN_LANGUAGE_v1.2.md。奶油白底、黑色粗边框、硬阴影、明亮分区色与大字层级；保留兴趣标签拖动回弹、按压反馈、可中断过渡和详情边缘返回。旧清新版保留为历史参考，不再作为开发视觉基线。真实 API 与持久化验收不因视觉变化而减少。

手机优先围绕发现、招募、发布、消息、我的组织。招募使用便于比较时间、人数和岗位的列表；条件、未知项和当前操作保持可见。趣味性主要来自四区识别、友好文案和轻量反馈，不通过额外积分或复杂动画增加范围。

## 每个功能的完成标准

完成意味着用户界面、真实API、数据库持久化、权限、关键失败处理、必要验证和使用说明均已具备。UI稿完成、生成了代码、页面有按钮，都不能单独视为功能完成。每次报告给出：完成的用户行为、关键变化、实际检查、未完成项和下一步。

AI开发过程材料从第一天记录。至少三条完整Prompt链最终应来自实际核心迭代；可关注招募草稿结构、并发岗位名额及退出撤权，但不预设必须制造某个Bug。

运行复现要记录环境、依赖、迁移、seed和实测耗时。开发演进复现要保留Prompt、必要上下文、使用工具与模型信息、人的决策、提交及可重复验证脚本。是否要求重新调用模型产生相同代码、10分钟是否包含依赖下载，应向赛事方确认，不能凭模型随机输出承诺确定性。

按用户提供要求准备5—8分钟1080p MP4，其中至少2分钟展示真实AI协同过程；技术PDF不超过30页，重点解释意图控制、架构和复现。研发规格可以独立保留，不直接用长规格替代参赛PDF。

## 第7天总结的固定格式

周总结模板位于docs/weekly/WEEK_01_REVIEW.md。每周复制为相应周次，先填写实际结果，再生成下一周计划。

必须回答：本周原定目标；实际完成及演示路径；实际投入；验收和测试证据；未完成与原因；真实用户反馈；关键AI协同案例；产品与UI变更；风险；下周目标、任务和验收标准。

不使用“基本完成”掩盖尚未联调的功能，不预填试用结果和测试通过状态。每周复盘后产出下一周计划文件，明确其依据的提交版本。
