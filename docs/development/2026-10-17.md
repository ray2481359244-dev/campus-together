## 1 注册与会话事务修正

原实现先独立创建 User / Profile，再开事务生成 Session。专用测试库临时触发器让登录会话插入失败，原流程返回 503 后实际留下 1 个用户，确认数据库失败处理不完整。

现在密码哈希在事务外计算；事务中检查学校、创建用户及资料、按条件撤销旧上下文、创建新会话。成功提交后才发送 Cookie。存储失败时整个事务回滚，旧匿名上下文仍有效；移除测试触发器后可以用同一邮箱正常注册。故障仅注入 `_test` 库，finally 删除触发器与函数，不触碰主库。

登录轮换和注销都只能成功争用仍有效且未撤销的旧会话。并发请求可能在 CSRF 校验阶段被拒绝（403），也可能在数据库条件更新阶段冲突（409）；只允许一个成功，拒绝响应不设置 / 清除 Cookie，防止旧请求破坏后来建立的登录状态。

## 2 防止跨标签页误用账号

普通标签页共享 Cookie，但 React 表单和 CSRF 状态各自保留。原界面在另一标签页换账号后没有一致性核对，不能让原页面自动刷新凭证后以新账号提交旧内容。

客户端对写入、CSRF 获取和可能包含私有内容的读取携带预期用户 ID；服务端把它与实际 Cookie 会话比较，不同账号返回 SESSION_CHANGED，原会话已失效返回 AUTH_REQUIRED。头字段只保证界面 / 会话一致，不授予任何权限，原 Cookie、CSRF、Origin 和作者检查继续执行。

BroadcastChannel 仅传递身份变化事件，不传 Cookie、CSRF 或个人资料。收到注销 / 切换事件后，其他标签页清理缓存与当前表单，显示恢复页等待用户重新加载。浏览器不支持或限制该通知 API 时不让应用崩溃，仍由下一次账号相关请求的服务端检查兜底。

普通失败保留输入与身份变化清理分开：前者帮助用户重试，后者避免旧账号内容流入新账号。已经保存的草稿仍归原账号；尚未提交内容不是自动备份。

## 3 迟到响应与状态恢复

仅比较用户 ID 不足以区分退出后又登录同一账号的上下文，因此请求还记录本地会话版本。自动 CSRF 重试沿用开始时的上下文；身份 / 版本已经变化的旧响应不更新新页面。

同时覆盖失败和成功：退出后到达的 401 不再把当前页面错误地切到新的过期提示；退出前已经保存的资料即使迟到返回 200，也不会再次调用旧资料恢复已退出用户。已经在旧会话合法提交的数据不因随后注销而自动撤回，本轮只保证页面认证状态不被旧结果覆盖。

登录、发布讨论、招募编辑页在登录态读取失败时明确显示重试，而不是直接认定为匿名；初始化未完成时先等待，避免账号上下文不明时进入表单。资料保存 503 的输入保留、同身份 CSRF 更新后重试和刷新读取均经过浏览器检查。
